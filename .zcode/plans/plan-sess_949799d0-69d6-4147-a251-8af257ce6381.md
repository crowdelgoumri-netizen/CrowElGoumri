# CrowdShipping v1 — Build Plan

## Scope locked (from your answers)
- **Surface:** React Native + Expo mobile app (iOS + Android) + thin Next.js admin
- **Escrow:** Stripe Connect (platform holds funds, manual release on delivery). Testable today in test mode; real money needs a company entity + Stripe Connect activation (parallel workstream, doesn't block build)
- **Corridor:** France → Algeria diaspora route, EUR-only (sidesteps the DZD non-convertibility problem)
- **Build style:** Modular monolith backend (not the blueprint's 8 microservices — that's scale architecture, wrong for a solo start). We can extract services later only where real pain appears.

## What I'm NOT building in v1 (deliberately cut)
- Lemonway / true PSD2 escrow → Stripe Connect now, upgrade later
- Customs declaration engine (Partie 4) → manual + ToS disclaimer for v1
- Insurance product → stub the data model, skip the partner integration
- Dispute mediation UI → basic "flag transaction" + admin handles manually
- Native push via FCM/APNS → Expo Push (one SDK, covers both)
- Kafka event bus → in-process event emitter; upgrade when throughput demands
- The matching service in Rust/Go → TypeScript port of the exact same algorithm from the blueprint

## The 6-week build, phased

### Phase 0 — Foundation (days 1-3)
- Init pnpm monorepo, TypeScript base configs, git
- `packages/db`: Prisma schema (the blueprint's full schema, **with the 3 fixes** below), Postgres 16 in Docker, first migration
- `packages/api`: Fastify skeleton, env validation (zod), health check, Prisma client wiring
- **Schema fixes I'll apply** (bugs in the blueprint I found during extraction):
  1. `Dispute.openedBy String` + `openedById User @relation(...)` conflict → make `openedById String` the FK scalar, `openedBy User @relation(fields:[openedById])` the relation
  2. `Trip.parcels` missing back-relation annotation → add explicit `@relation("Trip")`
  3. `GeoIndex` model with `Json` location is non-functional for real geo queries → drop it; use raw PostGIS queries via Prisma's `$queryRaw` instead (the matching algorithm already assumes PostGIS/Redis GEO)

### Phase 1 — Auth & KYC (days 4-8)
- Email/password + phone (Twilio Verify) signup
- JWT auth (access + refresh), Fastify plugin
- KYC: integrate **Sumsub** (blueprint's preferred, supports Algerian ID + Arabic OCR) — but ship behind a feature flag so you can launch with manual review if Sumsub KYB isn't ready
- Trust score seeding (the blueprint's 8-factor weighted score, computed on KYC completion)

### Phase 2 — Core domain: Parcels & Trips (days 9-16)
- `Parcel` CRUD: post a parcel (description, weight, dimensions, photos→S3, pickup/delivery address via the Algeria fallback addressing JSON, urgency, offered price)
- `Trip` CRUD: post a trip (route, schedule, mode, capacity, price/kg)
- Photo upload → S3 (Wasabi for cost) via presigned URLs
- Address handling: the blueprint's 5-level fallback system (geocode → PIN → POI → live-location → human relay) as a typed JSON column + a picker UI

### Phase 3 — Matching engine (days 17-22)
- `packages/matching`: TypeScript port of the blueprint's `compute_matching_score` (8 weighted subscores, hard-constraint filters, 30/100 threshold, 5-result top-N)
- Geo pre-filter: PostGIS `$queryRaw` for candidates within route corridor + time window (200 candidate pool)
- Matching endpoint: `GET /parcels/:id/matches` and `GET /trips/:id/matches` (bidirectional)
- Accept/reject flow → updates `Parcel.matchedTripId`, `Trip.currentWeightKg`

### Phase 4 — Escrow (Stripe Connect) (days 23-30)
- `EscrowService` module: the blueprint's EUR→EUR flow, adapted to Stripe Connect
  - Sender funds → Stripe PaymentIntent with `transfer_group = parcelId`
  - Funds land on platform balance (held)
  - On delivery confirmation → `POST /v1/transfers` to traveler's Connected Account (fee skimmed automatically: `amount - platformFee`)
- Traveler onboarding: Stripe Connect Express accounts (Stripe handles the KYC for payouts — this solves your payout-side compliance for free)
- Webhooks: `payment_intent.succeeded`, `transfer.created`, `charge.refunded`
- EscrowLedger state machine: `FUNDED → LOCKED → RELEASED` (+ `REFUNDED_SENDER` on cancel-before-pickup)

### Phase 5 — Delivery + chat + notifications (days 31-38)
- **Delivery handshake:** 6-digit PIN (sender generates, shares out-of-band, traveler enters) OR QR code. On match → `parcel.status = DELIVERED` → triggers escrow release
- **Chat:** Socket.IO room per parcel (sender ↔ traveler). Messages stored in Postgres for v1 (skip MongoDB — fewer moving parts); migrate later if volume demands
- **Notifications:** Expo Push (covers iOS+Android with one token), fallback to email via AWS SES. Notification types: MATCH_FOUND, PARCEL_PICKED_UP, IN_TRANSIT, DELIVERED, PAYOUT_SENT

### Phase 6 — Mobile app (Expo) (days 39-50)
The screens, in priority order:
1. Auth flow (login/signup/KYC entry)
2. Home: "I'm sending" / "I'm traveling" toggle
3. Post parcel / post trip (with photo upload, address picker)
4. Browse matches (with the score + reasoning badges: "★ Trusted traveler", "⚡ Arrives in time")
5. Parcel/trip detail + accept/reject + chat entry
6. Escrow: fund payment sheet (Stripe React Native SDK)
7. Delivery: enter PIN / scan QR
8. Ratings (post-delivery)
9. History / dashboard
- NativeWind v4 for styling (Tailwind for RN, matches blueprint)
- Mapbox RN for maps (blueprint's choice — better Algeria coverage than Google, cheaper)

### Phase 7 — Admin + launch prep (days 51-56)
- Next.js admin: user list/ban, dispute queue, manual escrow release override, payout status dashboard
- Stripe Connect activation guide (the legal/company workstream you run in parallel)
- Deployment: API → Fly.io or Railway (cheap, Postgres add-on); mobile → EAS Build + Submit

## The honest risks
1. **Stripe Connect is not legal escrow** — you hold funds on your platform balance, which at scale draws regulatory attention. Fine for launch/low volume, upgrade to Lemonway (blueprint's true escrow) before you process meaningful volume.
2. **KYC is the slowest external dependency** — Sumsub needs a company to activate. The feature-flag/manual-review fallback lets you launch without it.
3. **The matching algorithm is the moat, but it's only as good as its data** — with no historical transactions, `S_history` and `S_compatibility` start at neutral (0.5). It gets smarter as you get volume. That's expected and fine.
